# v10 lost 10.8s, for two reasons, and one of them is a process failure

2026-09-10

    v8   300.35
    v10  311.15   +10.79

Both changes in v10 had won 3 of 3 folds. The stack regressed. Our best stays
v8; rank 38 of 103 (the field grew from 95).

## Reason one: the two paths disagreed about ORDER

`--bulk-plan-only` filters the training rows. `--residual` fits a least-squares
baseline on them. The two files did those in opposite orders:

    crossval:  filter to plan rows  ->  fit baseline on the filtered frame
    final:     fit baseline on ALL rows  ->  then filter

Same operations, different baseline, different target. **v10 shipped a
configuration no fold ever tested.**

That is the seventh time crossval and final have disagreed about how to ship a
validated result, and the first where I introduced the disagreement myself --
by patching both files by hand and checking that both *had* the flag rather than
that both *did the same thing with it*. The parity guard I wrote a few hours
earlier checks that each parser defines every setting. It cannot see this,
because both parsers defined `--bulk-plan-only` correctly and the difference was
in the code underneath.

Fixed by extraction, not by matching: `crossval.prepare_residual()` now does
filter-then-baseline once, and both entry points call it.

## Reason two: I shipped a combination nothing had tested

`--bulk-plan-only` was measured alone. LFPG/LSZH routing plus `callsign_op` was
measured alone. **The combination was never run.** I reasoned that they touch
different halves of the model and therefore stack, and shipped on that
reasoning.

The reasoning is not obviously wrong -- one changes which rows the global model
sees, the other changes which no-plan model predicts a row -- but they are not
independent. The global model's predictions on no-plan rows are discarded, and
`--bulk-plan-only` removes exactly those rows from its training set, which
changes the residual scale the no-plan model is fitted against. That coupling
existed and I did not look for it.

So the honest state is that I have two candidate causes and cannot separate them
from the board alone.

## What actually stands

- v8's configuration, at 300.35, is the best thing we have and is unaffected --
  with `bulk_plan_only` off, `prepare_residual` reproduces exactly what v8 did.
- The two fold results are still real, on the metric each was judged on.
- What is NOT established is that they combine, or that either transfers with
  the baseline fitted the way final fits it.

## Next, in order

1. Fold-test the actual combination, against the same control, on folds 1,3,5.
   Not the parts. The thing that would ship.
2. Only then rebuild.

The rule I broke is one this project already learned in week one and wrote down:
ship what the folds measured, not something adjacent to it.
